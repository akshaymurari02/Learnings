================================================================================
          FACADE DESIGN PATTERN & EVOLUTIONARY ARCHITECTURE
================================================================================

[ PROBLEM: SUBSYSTEM COMPLEXITY & TIGHT COUPLING ]
When completing a high-level business task (e.g., placing an order, rendering a video, 
or shutting down a server cluster), the client often needs to interact with multiple 
low-level services or libraries.

WITHOUT A FACADE:
The client (e.g., API Controller, UI layer) must directly instantiate, configure, 
and execute each subsystem class in a precise order:

  InventoryService inventory = new InventoryService();
  PaymentGateway payment = new PaymentGateway();
  LogisticsService logistics = new LogisticsService();
  NotificationService notification = new NotificationService();

  if (inventory.check(itemId)) {
      if (payment.charge(userId, amount)) {
          String trackId = logistics.ship(itemId, address);
          notification.email(userId, trackId);
      }
  }

Drawbacks:
- Client is tightly coupled to 4+ subsystem APIs and their concrete implementations.
- Duplication of orchestration logic across Web, Mobile, and Admin entry points.
- Breaks Law of Demeter: The client knows far too much about inner system mechanics.

[ SOLUTION ]
Provide a single, simplified high-level interface (`OrderProcessingFacade`) that masks 
subsystem complexity. The client calls one intuitive entry point: `facade.placeOrder(...)`.


--------------------------------------------------------------------------------
 1. CORE DISTINCTION: ORCHESTRATION VS. CORE LOGIC
--------------------------------------------------------------------------------

- Subsystems (Core Logic)  : Handle specific domain work (e.g., calculating tax, 
                             formatting payment payloads, generating tracking numbers).
- Facade (Orchestration)   : Manages the high-level workflow (knowing WHICH services 
                             to call, in WHAT order, and handling high-level failures).


--------------------------------------------------------------------------------
 2. THE EVOLUTIONARY DESIGN PATH (PHASE 1 -> PHASE 2)
--------------------------------------------------------------------------------

A pragmatic design follows YAGNI ("You Aren't Gonna Need It") by starting simple 
and evolving as system complexity grows.

PHASE 1: Simple Facade (Direct Method Orchestration)
- Best when steps are fixed, simple, and rarely change.
- The Facade directly calls subsystem methods sequentially.

PHASE 2: Refactored Facade (Chain of Responsibility / Pipeline under the hood)
- Required when complexity grows: dynamic step execution, short-circuiting on failure, 
  custom fraud checks, or conditional steps (e.g., digital items skip shipping).
- CRITICAL ARCHITECTURAL BENEFIT: The public API of the Facade (`facade.placeOrder()`) 
  NEVER CHANGES. External clients remain 100% unaware of the internal refactoring!


--------------------------------------------------------------------------------
 3. IMPLEMENTATION STRUCTURE (JAVA EXAMPLE)
--------------------------------------------------------------------------------

// 1. Core Logic Subsystem Classes
public class InventoryService {
    public boolean reserve(String item) { System.out.println("Reserved: " + item); return true; }
}
public class PaymentGateway {
    public boolean charge(double amt) { System.out.println("Charged: $" + amt); return true; }
}
public class ShippingService {
    public String ship(String addr) { System.out.println("Shipped to: " + addr); return "TRK-1001"; }
}

// -----------------------------------------------------------------------------
// PHASE 1: Simple Facade Implementation
// -----------------------------------------------------------------------------
public class OrderFacadeSimple {
    private final InventoryService inventory = new InventoryService();
    private final PaymentGateway payment = new PaymentGateway();
    private final ShippingService shipping = new ShippingService();

    public boolean placeOrder(String item, double amount, String address) {
        if (!inventory.reserve(item)) return false;
        if (!payment.charge(amount)) return false;
        shipping.ship(address);
        return true;
    }
}

// -----------------------------------------------------------------------------
// PHASE 2: Refactored Internal Engine (Facade + Chain Pipeline)
// -----------------------------------------------------------------------------
// Context object passed along the chain
public class OrderContext {
    public String item;
    public double amount;
    public String address;
    public boolean isSuccess = true;
    public String failureReason;
}

// Handler interface
public abstract class OrderHandler {
    protected OrderHandler next;
    public OrderHandler setNext(OrderHandler next) { this.next = next; return next; }
    
    public void execute(OrderContext ctx) {
        if (!ctx.isSuccess) return; // Short-circuit on failure
        process(ctx);
        if (next != null && ctx.isSuccess) next.execute(ctx);
    }
    protected abstract void process(OrderContext ctx);
}

// Concrete Handlers
public class FraudCheckStep extends OrderHandler {
    protected void process(OrderContext ctx) { System.out.println("Step 1: Fraud Check Passed."); }
}
public class InventoryStep extends OrderHandler {
    protected void process(OrderContext ctx) { System.out.println("Step 2: Inventory Reserved."); }
}
public class PaymentStep extends OrderHandler {
    protected void process(OrderContext ctx) { System.out.println("Step 3: Payment Processed."); }
}

// The Facade Class (Client Interface remains identical)
public class OrderProcessingFacade {
    private final OrderHandler pipelineHead;

    public OrderProcessingFacade() {
        // Build internal pipeline
        OrderHandler fraud = new FraudCheckStep();
        OrderHandler stock = new InventoryStep();
        OrderHandler pay = new PaymentStep();

        fraud.setNext(stock).setNext(pay);
        this.pipelineHead = fraud;
    }

    // Public method signature stays unchanged!
    public boolean placeOrder(String item, double amount, String address) {
        OrderContext ctx = new OrderContext();
        ctx.item = item; ctx.amount = amount; ctx.address = address;

        // Delegates execution to the internal dynamic pipeline
        pipelineHead.execute(ctx);

        return ctx.isSuccess;
    }
}


--------------------------------------------------------------------------------
 4. SOLID PRINCIPLES & ARCHITECTURAL BENEFITS
--------------------------------------------------------------------------------

1. Principle of Least Knowledge (Law of Demeter)
   - Client talks ONLY to the Facade, shielding it from internal subsystem details.

2. Single Responsibility Principle (SRP)
   - Orchestration logic is concentrated in the Facade/Pipeline, keeping UI and 
     API controllers thin and clean.

3. Open/Closed Principle (OCP)
   - New pipeline steps (e.g., `CouponValidationStep`) can be inserted into the 
     internal chain without altering existing handler code or breaking client code.


--------------------------------------------------------------------------------
 5. PATTERN COMPARISON
--------------------------------------------------------------------------------

+-------------------+----------------------------------------------------------+
| Pattern           | Intent & Key Focus                                       |
+-------------------+----------------------------------------------------------+
| Facade            | Simplifies access to a COMPLEX SUBSYSTEM via one interface.|
| Adapter           | Translates an INCOMPATIBLE interface to match an expected one.|
| Decorator         | Dynamically ADDS BEHAVIOR/RESPONSIBILITY to an object.   |
| Chain (Pipeline)  | Routes a request through a SEQUENTIAL LIST of handlers.  |
+-------------------+----------------------------------------------------------+
